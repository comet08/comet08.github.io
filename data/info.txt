    Socket | [행동]
•stomp를   사용했기 때문에 별도의 프로토콜 대응이 필요하여 WebSocket   mocking 도구를   설계.
•bun.js   기반 STOMP   mock 서버와   UI   Devtool을   만들어  메시지를 받을 수 있는 도구를 개발.
•도구를   패키지 형태로 분리하고,   각   프로젝트에서 핸들러 주입 방식으로 재사용할 수 있도록 구조를 설계.
 
[성과/근거]
•mock   server로   미리 스펙 기반 기능을 개발하여 MVP   완수.
•이후   메인을 개발하면서도 사내망 SSO   연동으로   로컬에서의 테스트가 쉽지 않은 상황을 해결.
•클라이언트   연결 끊김,   재연결   구독 등의 여러 경우에 대해 mock   server로   모두 재현,   검증할   수 있어 실 서비스의 장애 가능성을 낮춤.
•신규/투입   개발자들도 STOMP   토픽에   대한 mock만   정의하면 바로 기능 확인이 가능해,  온보딩 속도와 학습 비용을 줄임.

| RestAPI | [상황]
1.   개발자가   각자 API   request/response 타입을   수동으로 작성하면서  타입 미스매칭, 필드   누락 등 휴먼 에러 발생.
2.   Rest API는 MSW로 mocking하고   있었으나,  API 수가 늘어나면서 어떤 handler가   어떤 API를   담당하는지 찾는 데 시간이 많이 소요.
3.   저장/상태   변경과 같은 플로우는 정적인 mock   response만으로는   실제 동작 흐름을 충분히 검증하기 어려운 상황.
 
[행동]
1.   백엔드   Swagger   스펙을   기반으로 openapi-generator를   도입.
   -API 타입을   자동으로 생성하는 스크립트를 구성하여 request/response   타입을  직접 작성하지 않도록 표준화.
2.   MSW 위에서   동작하는 MSW   GUI Controller 패키지를   개발.
    -특정   요청에 대한 응답을 GUI   화면에서   설정·저장하고   프리셋으로 재사용 할 수 있도록 설계.
    -GUI Controller용   인터페이스를 설계하고,   이를 MSW와   연동하는 핸들러 로직을 직접 구현.
    -기존 MSW   handler를 한   번에 갈아엎지 않고,   점진적   마이그레이션이 가능하도록 구조 설계.
3.   msw/data를   도입해 필요한 데이터 구조를 정의,   단순   정적 응답이 아니라 상태 변화가 반영되는 mock   데이터   흐름을 구성.
 
[성과/근거]
1.   openapi-generator 스크립트로   타입 정의를 자동화.
   -타입   미스매칭과 같은 휴먼 에러를 줄이고,   개발자가   타입을 직접 작성·수정하는   시간을 제거.
2. 기존에는   대부분의 개발자가 코드 베이스의 MSW   handler 파일을   열고 응답값을 임시 수정한 뒤,   
   -테스트   후 다시 변경 내역을 되돌리는 방식으로 사용하고 있었으나, 단일 GUI에서 여러 API   응답을   한 번에 조회·수정할   수 있어 
       mock 응답 관리 시간이 줄어들었음.
3. 정적인   데이터 mocking을   넘어 msw/data로 플로우에   따라 응답이 달라지는 동적인 시나리오까지 
    대응 가능해져 저장/상태   변경 등 실제 유저 플로우에 가까운 검증이 가능해짐.
